## 1. 페이지 목표와 성공 기준

### 1-1. 이 페이지가 해야 할 일

```
처음 보는 사람이 90초 안에
  ① 이게 무슨 문제를 푸는지 이해하고
  ② "내 얘기네"라고 느끼고
  ③ 설치 명령 한 줄을 복사한다
```

### 1-2. 성공 기준 (로그로 남길 수 있는 행동)

| 지표 | 정의 | 비고 |
|---|---|---|
| 설치 명령 복사 | 설치 블록의 복사 버튼 클릭 | **주 전환 지표** |
| 저장소 이동 | GitHub 링크 클릭 | 보조 전환 |
| 스크롤 완주 | 마지막 섹션 도달 비율 | 스토리텔링이 끝까지 붙드는가 |
| 데모 상호작용 | 워크스루 블록 조작 횟수 | 동작 이해도의 대리 지표 |

> `[미결 M-1]` 위 지표를 실제로 계측할지, 계측한다면 어떤 도구를 쓸지. 계측하지 않는다면 이 표는 설계 지향점으로만 남는다.

### 1-3. 하지 않을 것 (anti-goal)

- **규칙 전문을 옮기지 않는다.** SKILL.md는 에이전트가 읽는 문서다. 페이지는 "왜 이렇게 동작하는가"까지만 말하고 상세는 저장소로 넘긴다.
- **다른 도구를 깎아내리지 않는다.** 문제 제기는 "기존 방식"이라는 일반 범주까지만. 스킬 본문이 독립 스킬로 정리된 포지셔닝과 어긋나면 안 된다.
- **과장·감탄을 쓰지 않는다.** 스킬 자체가 "감정 절제"를 규칙으로 갖는다. 페이지가 그 규칙을 어기면 설득력이 깎인다.
- **기능 나열식 구성을 쓰지 않는다.** 11개 기능을 그대로 나열하면 논지가 사라진다. 오너십이라는 하나의 축으로 꿰어야 한다.

## 2. 독자

| | 독자 | 이 페이지에서 얻어야 할 것 | 주의 |
|---|---|---|---|
| **P1** | AI 에이전트로 실무를 굴리는 사람 (개발·기획 무관) | "결정이 새는 지점"에 대한 언어와 그 처방 | 1순위 독자 |
| **P2** | 비개발 기획·연구·사무 실무자 | "이건 개발자용이 아니다"라는 확신 | 도메인 예시로 증명해야 함 |
| **P3** | 스킬을 팀에 도입하려는 사람 | 설치 범위(개인/프로젝트)와 팀 공유 방식 | 설치 섹션에서 해소 |

**P2가 이 페이지의 난이도를 결정한다.** 스킬 자체가 비개발 독자를 배려하도록 설계되어 있으므로, 페이지도 같은 기준을 지켜야 한다 — 전문용어를 던지지 않고, 원어를 쓸 때는 역어와 뜻풀이를 함께 둔다(스킬의 §8 규칙을 페이지가 스스로 지키는 것 자체가 데모가 된다).

## 3. 핵심 메시지

### 한 문장

> **실행은 맡기고, 결정은 쥔다.**

### 세 문장

> AI에게 일을 맡길 때 오너십이 새는 곳은 실행이 아니라 결정이다.
> GRIP IT은 착수 전에 아직 정해지지 않은 결정을 전부 꺼내 하나씩 함께 정하고,
> 그 결정을 문서에 고정해 이후 AI 작업이 따르게 만든다.

### 제목 해설 (페이지 어딘가에서 한 번은 풀어야 할 것)

| 조각 | 의미 |
|---|---|
| **핸즈오프(hands-off)** | 실행에 손을 떼는 것. 이건 우리가 원하는 것이다 |
| **오너십** | 그런데 실행에서 손을 떼면 결정까지 함께 놓치기 쉽다. 놓치지 않는 것이 오너십 |
| **그립(grip)** | 실행은 놓되 이해·방향·결정은 단단히 쥐는 상태 |
| **AI-Native** | 이 긴장을 사람이 참아서가 아니라 **에이전트 절차 자체로** 푸는 방식 |

> `[미결 M-2]` 제목의 영문 표기를 `GRIP IT`으로 할지 `Grip It`으로 할지. 스킬 식별자는 `grip-it`(하이픈 소문자)이므로 **본문에서 스킬을 가리킬 때는 `grip-it`, 브랜드로 부를 때는 `GRIP IT`**으로 나누기를 제안한다. 결정 필요.

## 4. 단계적 스토리텔링 전략 (초안 — 이 문서의 핵심)

### 4-1. 설계 원리

독자의 심리 상태를 **불편함 → 명명 → 납득 → 확인 → 행동** 순으로 옮긴다. 각 단계는 다음 단계로 넘어갈 **전환 장치**를 하나씩 갖는다. 기능은 단계 안에서만 등장하며, 단독으로 나열되지 않는다.

```
S0 후킹      실행은 맡기고, 결정은 쥔다
   ↓ 그런데 실제로는 그게 잘 안 된다
S1 공감      그립이 풀리는 네 장면
   ↓ 이 넷의 공통점은 무엇인가
S2 명명      오너십은 실행이 아니라 "결정"에서 샌다
   ↓ 그럼 그냥 AI가 많이 물어보면 되지 않나
S3 반전      더 캐묻는 방식은 이미 실패했다 (피로)
   ↓ 그럼 무엇을 다르게 하나
S4 전환      사람이 아니라 "문제"를 붙잡는다
   ↓ 구체적으로 어떻게
S5 원리      그립을 만드는 여섯 장치
   ↓ 말고 실제로 보여달라
S6 증거      한 세션을 처음부터 끝까지
   ↓ 그런데 이거 개발자용 아닌가
S7 범용      다섯 도메인에서 같은 절차
   ↓ 끝나면 무엇이 남나
S8 자산      기록계층과 확정계층
   ↓ 지금 시작하려면
S9 행동      설치 세 줄
```

### 4-2. 단계별 상세

---

#### S0 — 후킹 (Hero)

| | |
|---|---|
| **독자 상태** | 아직 아무 맥락 없음 |
| **목적** | 3초 안에 "이 페이지가 무엇에 관한 것인지" 각인 |
| **핵심 문장** | **실행은 맡기고, 결정은 쥔다** |
| **부제** | AI 에이전트에게 일을 맡길 때, 우리가 놓치고 싶지 않은 단 하나 |
| **보조 요소** | 스킬 한 줄 정의 + 설치 명령 미리보기 + GitHub 링크 |
| **전환 장치** | 마지막 줄에 균열을 낸다 — *"그런데 실제로 해보면, 결정까지 함께 넘어가 있습니다."* |

> 히어로에서 **설치 명령을 이미 한 번 보여준다.** 결정이 빠른 독자를 붙잡기 위한 것이고, 뒤의 S9와 중복이 아니라 **의도된 두 번의 기회**다.

---

#### S1 — 공감: 그립이 풀리는 네 장면

| | |
|---|---|
| **독자 상태** | "그래서 뭐?" |
| **목적** | 독자가 겪은 장면을 그대로 재현해 "내 얘기"로 만들기 |
| **구성** | 네 장면을 각각 한 문장 + 한 컷으로 |

```
① 근거가 부족해도 AI가 그럴듯한 항목을 지어낸다
② 뜻을 모르는 용어가 섞인 제안을 그대로 승인한다
③ AI가 내놓은 보기 안에서만 고르게 된다
④ 정한 내용이 대화에 흩어져, 다음 세션의 AI가 또 제멋대로 정한다
```

| | |
|---|---|
| **닫는 문장** | **결정은 분명 내 것이었는데, 결과물은 내 것이 아니게 됩니다.** |
| **전환 장치** | *"이 네 장면에는 공통점이 하나 있습니다."* |

> 이 섹션이 페이지 전체의 이탈률을 좌우한다. 네 장면 중 하나라도 자기 경험과 맞으면 끝까지 읽는다.

---

#### S2 — 명명: 오너십은 결정에서 샌다

| | |
|---|---|
| **독자 상태** | "맞아, 그랬지" |
| **목적** | 흩어진 불편에 **이름**을 붙여 개념으로 승격 |
| **핵심 문장** | AI에게 일을 맡길 때 오너십이 새는 곳은 **실행이 아니라 결정**이다 |
| **보조** | 제목 해설(§3) — 핸즈오프 / 오너십 / 그립을 여기서 푼다 |
| **전환 장치** | *"그럼 AI가 더 많이 물어보게 하면 되지 않을까요?"* — 독자가 떠올릴 반론을 먼저 꺼낸다 |

---

#### S3 — 반전: 더 캐묻는 방식은 이미 실패했다

| | |
|---|---|
| **독자 상태** | "물어보게 하면 되잖아" |
| **목적** | 뻔한 해법을 먼저 무너뜨려 다음 해법의 자리를 만든다 |
| **핵심 논지** | 답을 캐내려 몰아붙이면 정보는 얻어도, 사용자가 지쳐 **대충 답하거나 중간에 그만둔다** |
| **강조점** | 피로는 불쾌감이 아니라 **답변 품질 저하와 이탈**이라는 기능적 손실이다 |
| **전환 장치** | *"문제는 질문의 양이 아니라, 무엇을 추궁하느냐에 있었습니다."* |

---

#### S4 — 전환: 사람이 아니라 문제를 붙잡는다

| | |
|---|---|
| **독자 상태** | "그럼 뭘 다르게 하는데?" |
| **목적** | 이 스킬의 관점 전환을 한 번에 심기 |
| **핵심 대비** | 추궁의 대상을 **사람 → 문제**로 옮긴다 |
| **표현** | *"왜 아직 안 정하셨나요?"* ↔ *"이 문제의 이 지점이 아직 정해지지 않았습니다."* |
| **부연** | 모든 질문에 **권장안 + 근거**가 붙어, 사용자는 답을 새로 만들지 않고 **확인·교정**만 한다 |
| **전환 장치** | *"관점을 바꾸면 절차도 바뀝니다. 여섯 가지가 달라집니다."* |

---

#### S5 — 원리: 그립을 만드는 여섯 장치

| | |
|---|---|
| **독자 상태** | "말은 좋은데 구체적으로?" |
| **목적** | S1의 네 장면에 **일대일로 대응하는 처방**을 보여 논리를 닫는다 |
| **구성 원칙** | 기능 나열이 아니라 **"새는 지점 ↔ 장치"** 대응표 |

| 오너십이 새는 지점 | GRIP IT의 장치 |
|---|---|
| 근거가 부족해도 그럴듯한 항목을 지어낸다 | **재료 점검 게이트** — 기준선이 없으면 토픽을 뽑지 않습니다 |
| 전체 판을 모른 채 질문에 끌려간다 | **토픽 전체를 미리 보여주기** — 몇 번 문답할지 처음부터 압니다 |
| 뜻을 모르는 제안을 그대로 승인한다 | **용어 해설 + 설명적 대화체** — 이해한 것만 결정합니다 |
| AI가 제시한 보기 안에서만 고른다 | **기타(직접 입력) 상시 옵션** — 내 방식으로 답할 수 있습니다 |
| 정한 내용이 대화에 흩어진다 | **결정 기록부** — 무엇을 왜 정했는지 남습니다 |
| 다음 세션의 AI가 다시 제멋대로 정한다 | **규범 문서에 고정** — 한 번 정한 것은 다시 협상되지 않습니다 |

| | |
|---|---|
| **닫는 문장** | 에이전트는 재료를 점검하고, 선택지와 근거를 차려 놓고, 용어를 풀어 설명합니다. **결정은 사용자가 합니다.** |
| **전환 장치** | *"실제로는 이렇게 흘러갑니다."* |

> 각 장치는 **한 줄 요약 + 펼치면 근거**의 2단 구조를 권한다. 여섯 개를 모두 펼쳐 놓으면 S5에서 페이지가 무거워진다.

---

#### S6 — 증거: 한 세션을 처음부터 끝까지

| | |
|---|---|
| **독자 상태** | "정말 그렇게 동작하나?" |
| **목적** | **말하지 말고 보여주기.** 이 페이지에서 가장 공들일 섹션 |
| **소재** | 연구 도메인 시나리오 — 비개발 독자를 향한 포지셔닝을 동시에 증명한다 |

**보여줄 4컷**

```
1컷  재료 점검   R1 충족 / R2 없음 → 게이트 발동, A·B 두 갈래만 제시
2컷  토픽 원장   RESOLVED 0 / DROPPED 0 / TOTAL 4 — 앞으로 몇 번인지가 여기서 보인다
3컷  한 토픽     선택지 + 권장안·근거 + [용어] 해설 + 마지막에 "기타(직접 입력)"
4컷  반영 완료   근거 문서 / 규범 문서 / 기록부 세 줄
```

| | |
|---|---|
| **강조 포인트** | 2컷의 카운터와 3컷의 `기타` 옵션. 이 둘이 "가시성"과 "출구"를 눈으로 증명한다 |
| **전환 장치** | *"이 예시는 연구였습니다. 사업기획이라면, 서비스기획이라면요?"* |

> `[미결 M-3]` 이 4컷을 **정적 코드블록**으로 둘지, **단계 이동 인터랙션**으로 만들지, **자동 재생 애니메이션**으로 만들지. §7-7에 세 안을 정리했다.

#### S7 — 범용: 다섯 도메인에서 같은 절차

| | |
|---|---|
| **독자 상태** | "개발자용 아닌가?" — 페이지 최대의 반론 |
| **목적** | 도메인 무관성을 **주장이 아니라 표로** 증명 |
| **구성** | 사업기획 · 서비스기획 · 연구 · 일반 사무 · 소프트웨어 5열 |

| 역할 | 사업기획 | 서비스기획 | 연구 | 일반 사무 |

## 6. 콘텐츠 원칙

1. **스킬의 언어 규칙을 페이지가 스스로 지킨다.** 완결 문장, 경어 기조, 감정 절제, 영문 용어는 `English Term(역어: 뜻풀이)`. 페이지가 규칙을 어기면 규칙의 설득력이 사라진다.
2. **숫자는 검증 가능한 것만 쓴다.** "몇 배 빨라진다" 같은 미측정 주장 금지. 쓸 수 있는 것은 구조적 사실뿐이다 — 도메인 5종, 재료 역할 5개, 장치 6개, 종료 사유 4종.
3. **한 섹션 한 메시지.** 두 개를 담고 싶으면 섹션을 쪼갠다.
4. **모든 주장 뒤에 근거 한 줄.** 스킬이 "권장안 + 근거"를 규칙으로 갖는 것과 같은 태도.

> `[미결 M-6]` 페이지를 **한국어 단일**로 낼지, **한/영 병행**으로 낼지. 저장소는 README 한/영을 모두 갖추고 있다.

## 7. 시각적 표현 기획 `[전 항목 미결]`

### 7-1. 비주얼 컨셉 `[미결 V-1]`

세 방향을 후보로 둔다.

| 안 | 컨셉 | 근거 | 위험 |
|---|---|---|---|
| **A. 손과 쥠** | 그립 은유를 물리적으로 — 놓는 손/쥐는 손 | 제목과 직결, 기억에 남음 | 진부해지기 쉽고 손 이미지가 촌스러워질 수 있음 |
| **B. 계기판** | 결정을 계기·눈금으로 — 카운터·게이지 | 원장 카운터·진척 표시와 자연스럽게 연결 | 차갑고 기계적으로 보일 수 있음 |
| **C. 문서 계층** | 흩어진 메모 → 정돈된 두 계층 | 산출물이 파일이라는 핵심과 일치 | 시각적 임팩트가 약함 |

**초안 제안:** A를 히어로에만 쓰고, 본문은 B의 계기 요소(카운터·진척)로 끌고 간다. C는 S8에서만 등장.

### 7-2. 컬러 시스템 `[미결 V-2]`

**초안 방향**

```
바탕      매우 밝은 중립색 (종이에 가까운 오프화이트)
본문      고대비 뉴트럴 다크
강조 1    "쥠"을 상징하는 단일 강조색 — 채도 높은 한 색만
강조 2    상태색 (RESOLVED / UNRESOLVED / DROPPED) — 3색
```

- 강조색을 **하나만** 쓰는 편을 권한다. 스킬의 "감정 절제" 규칙과 정합한다.
- 상태 3색은 데모 블록에서만 쓰고 본문에는 쓰지 않는다.

> 결정 필요: 강조색 지정 · 다크 모드 지원 여부 · 상태 3색이 색맹 조건에서 구분되는지
