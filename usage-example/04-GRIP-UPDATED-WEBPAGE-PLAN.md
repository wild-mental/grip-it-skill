## 1. 페이지 목표와 성공 기준

### 1-1. 이 페이지가 해야 할 일

```
처음 보는 사람이 90초 안에
  ① 이게 무슨 문제를 푸는지 이해하고
  ② "내 얘기네"라고 느끼고
  ③ 설치 명령 한 줄을 복사한다
```

### 1-2. 성공 기준 (로그로 남길 수 있는 행동)

| 지표 | 정의 | 비고 |
|---|---|---|
| 설치 명령 복사 | 설치 블록의 복사 버튼 클릭 | **주 전환 지표** |
| 저장소 이동 | GitHub 링크 클릭 | 보조 전환 |
| 스크롤 완주 | 마지막 섹션 도달 비율 | 스토리텔링이 끝까지 붙드는가 |
| 데모 상호작용 | 워크스루 블록 조작 횟수 | 동작 이해도의 대리 지표 |

**계측하지 않는다 `[확정]`.** 분석 도구를 붙이지 않으므로 위 표는 측정 계획이 아니라 **설계 지향점**으로 읽는다.

그래도 표를 남겨 두는 이유가 있다. 카피와 배치를 정할 때 "이 요소가 설치 명령 복사에 기여하는가"를 물을 기준이 되기 때문이다. 숫자로 확인하지 않을 뿐, 설계의 잣대로는 계속 쓴다.

### 1-3. 하지 않을 것 (anti-goal)

- **규칙 전문을 옮기지 않는다.** SKILL.md는 에이전트가 읽는 문서다. 페이지는 "왜 이렇게 동작하는가"까지만 말하고 상세는 저장소로 넘긴다.
- **다른 도구를 깎아내리지 않는다.** 문제 제기는 "기존 방식"이라는 일반 범주까지만. 스킬 본문이 독립 스킬로 정리된 포지셔닝과 어긋나면 안 된다.
- **과장·감탄을 쓰지 않는다.** 스킬 자체가 "감정 절제"를 규칙으로 갖는다. 페이지가 그 규칙을 어기면 설득력이 깎인다.
- **기능 나열식 구성을 쓰지 않는다.** 11개 기능을 그대로 나열하면 논지가 사라진다. 오너십이라는 하나의 축으로 꿰어야 한다.

### 1-4. 제작 제약 `[확정 · T6에서 상향 갱신]`

**중간 투입.** 페이지는 한 장이되, 히어로의 손 연출을 제대로 만들기 위해 이미지 시퀀스와 모션 구현에 시간을 들인다.

| | |
|---|---|
| 산출 형태 | 페이지 한 장 (한·영 전환 포함) |
| 시각 작업 | 손 이미지 시퀀스 20장 내외 제작 + 스크롤 연동 모션 구현 |
| 기간 | 1~2주 |

처음에는 최소 투입(정적 한 장·기존 자산만·며칠)으로 정했으나, 비주얼 컨셉(§7-1)이 확정되면서 상향했다. 손 연출이 이 페이지의 주된 시각 논거이므로, 그 부분에는 투입하고 나머지는 가볍게 가져간다.

언어는 한·영 병행이되(§6) 시각 자산을 공유하고 카피만 두 벌로 만든다.

**투입을 집중할 곳과 아낄 곳**

| 집중 | 히어로 손 연출 — 이미지 시퀀스, 스크롤 반응, 쥐는 순간의 빛 연출 |
|---|---|
| **아낌** | 본문 섹션 — 기존 README 표·코드블록을 그대로 인용하고 별도 시각화를 만들지 않는다 |

## 2. 독자

| | 독자 | 이 페이지에서 얻어야 할 것 | 주의 |
|---|---|---|---|
| **P1** | AI 에이전트로 실무를 굴리는 사람 (개발·기획 무관) | "결정이 새는 지점"에 대한 언어와 그 처방 | 1순위 독자 |
| **P2** | 비개발 기획·연구·사무 실무자 | "이건 개발자용이 아니다"라는 확신 | 도메인 예시로 증명해야 함 |
| **P3** | 스킬을 팀에 도입하려는 사람 | 설치 범위(개인/프로젝트)와 팀 공유 방식 | 설치 섹션에서 해소 |

**P2가 이 페이지의 난이도를 결정한다.** 스킬 자체가 비개발 독자를 배려하도록 설계되어 있으므로, 페이지도 같은 기준을 지켜야 한다 — 전문용어를 던지지 않고, 원어를 쓸 때는 역어와 뜻풀이를 함께 둔다(스킬의 §8 규칙을 페이지가 스스로 지키는 것 자체가 데모가 된다).

## 3. 핵심 메시지

### 한 문장

> **실행은 맡기고, 결정은 쥔다.**

### 세 문장

> AI에게 일을 맡길 때 오너십이 새는 곳은 실행이 아니라 결정이다.
> GRIP IT은 착수 전에 아직 정해지지 않은 결정을 전부 꺼내 하나씩 함께 정하고,
> 그 결정을 문서에 고정해 이후 AI 작업이 따르게 만든다.

### 제목 해설 (페이지 어딘가에서 한 번은 풀어야 할 것)

| 조각 | 의미 |
|---|---|
| **핸즈오프(hands-off)** | 실행에 손을 떼는 것. 이건 우리가 원하는 것이다 |
| **오너십** | 그런데 실행에서 손을 떼면 결정까지 함께 놓치기 쉽다. 놓치지 않는 것이 오너십 |
| **그립(grip)** | 실행은 놓되 이해·방향·결정은 단단히 쥐는 상태 |
| **AI-Native** | 이 긴장을 사람이 참아서가 아니라 **에이전트 절차 자체로** 푸는 방식 |

### 표기 규칙 `[확정]`

| 쓰임 | 표기 | 예 |
|---|---|---|
| 브랜드로 부를 때 | **`GRIP IT`** | 페이지 제목, 히어로, 마무리 문장 |
| 스킬을 가리킬 때 | **`grip-it`** | 설치 명령, 호출(`/grip-it`), 경로, 본문에서 스킬 자체를 지칭 |

한 문장 안에 둘이 함께 오면 브랜드를 앞에 둔다 — *"GRIP IT은 `grip-it` 스킬로 설치합니다."*

## 4. 단계적 스토리텔링 전략 (초안 — 이 문서의 핵심)

### 4-1. 설계 원리

독자의 심리 상태를 **불편함 → 명명 → 납득 → 확인 → 행동** 순으로 옮긴다. 각 단계는 다음 단계로 넘어갈 **전환 장치**를 하나씩 갖는다. 기능은 단계 안에서만 등장하며, 단독으로 나열되지 않는다.

```
S0 후킹      실행은 맡기고, 결정은 쥔다
   ↓ 그런데 실제로는 그게 잘 안 된다
S1 공감      그립이 풀리는 네 장면
   ↓ 이 넷의 공통점은 무엇인가
S2 명명      오너십은 실행이 아니라 "결정"에서 샌다
   ↓ 그럼 그냥 AI가 많이 물어보면 되지 않나
S3 반전      더 캐묻는 방식은 이미 실패했다 (피로)
   ↓ 그럼 무엇을 다르게 하나
S4 전환      사람이 아니라 "문제"를 붙잡는다
   ↓ 구체적으로 어떻게
S5 원리      그립을 만드는 여섯 장치
   ↓ 말고 실제로 보여달라
S6 증거      한 세션을 처음부터 끝까지
   ↓ 그런데 이거 개발자용 아닌가
S7 범용      다섯 도메인에서 같은 절차
   ↓ 끝나면 무엇이 남나
S8 자산      기록계층과 확정계층
   ↓ 지금 시작하려면
S9 행동      설치 세 줄
```

### 4-2. 단계별 상세

---

#### S0 — 후킹 (Hero)

| | |
|---|---|
| **독자 상태** | 아직 아무 맥락 없음 |
| **목적** | 3초 안에 "이 페이지가 무엇에 관한 것인지" 각인 |
| **핵심 문장** | **실행은 맡기고, 결정은 쥔다** |
| **부제** | AI 에이전트에게 일을 맡길 때, 우리가 놓치고 싶지 않은 단 하나 |
| **보조 요소** | 스킬 한 줄 정의 + 설치 명령 미리보기 + GitHub 링크 |
| **전환 장치** | 마지막 줄에 균열을 낸다 — *"그런데 실제로 해보면, 결정까지 함께 넘어가 있습니다."* |

> 히어로에서 **설치 명령을 이미 한 번 보여준다.** 결정이 빠른 독자를 붙잡기 위한 것이고, 뒤의 S9와 중복이 아니라 **의도된 두 번의 기회**다.

---

#### S1 — 공감: 그립이 풀리는 네 장면

| | |
|---|---|
| **독자 상태** | "그래서 뭐?" |
| **목적** | 독자가 겪은 장면을 그대로 재현해 "내 얘기"로 만들기 |
| **구성** | 네 장면을 각각 한 문장 + 한 컷으로 |

```
① 근거가 부족해도 AI가 그럴듯한 항목을 지어낸다
② 뜻을 모르는 용어가 섞인 제안을 그대로 승인한다
③ AI가 내놓은 보기 안에서만 고르게 된다
④ 정한 내용이 대화에 흩어져, 다음 세션의 AI가 또 제멋대로 정한다
```

| | |
|---|---|
| **닫는 문장** | **결정은 분명 내 것이었는데, 결과물은 내 것이 아니게 됩니다.** |
| **전환 장치** | *"이 네 장면에는 공통점이 하나 있습니다."* |

> 이 섹션이 페이지 전체의 이탈률을 좌우한다. 네 장면 중 하나라도 자기 경험과 맞으면 끝까지 읽는다.

---

#### S2 — 명명: 오너십은 결정에서 샌다

| | |
|---|---|
| **독자 상태** | "맞아, 그랬지" |
| **목적** | 흩어진 불편에 **이름**을 붙여 개념으로 승격 |
| **핵심 문장** | AI에게 일을 맡길 때 오너십이 새는 곳은 **실행이 아니라 결정**이다 |
| **보조** | 제목 해설(§3) — 핸즈오프 / 오너십 / 그립을 여기서 푼다 |
| **전환 장치** | *"그럼 AI가 더 많이 물어보게 하면 되지 않을까요?"* — 독자가 떠올릴 반론을 먼저 꺼낸다 |

---

#### S3 — 반전: 더 캐묻는 방식은 이미 실패했다

| | |
|---|---|
| **독자 상태** | "물어보게 하면 되잖아" |
| **목적** | 뻔한 해법을 먼저 무너뜨려 다음 해법의 자리를 만든다 |
| **핵심 논지** | 답을 캐내려 몰아붙이면 정보는 얻어도, 사용자가 지쳐 **대충 답하거나 중간에 그만둔다** |
| **강조점** | 피로는 불쾌감이 아니라 **답변 품질 저하와 이탈**이라는 기능적 손실이다 |
| **전환 장치** | *"문제는 질문의 양이 아니라, 무엇을 추궁하느냐에 있었습니다."* |

---

#### S4 — 전환: 사람이 아니라 문제를 붙잡는다

| | |
|---|---|
| **독자 상태** | "그럼 뭘 다르게 하는데?" |
| **목적** | 이 스킬의 관점 전환을 한 번에 심기 |
| **핵심 대비** | 추궁의 대상을 **사람 → 문제**로 옮긴다 |
| **표현** | *"왜 아직 안 정하셨나요?"* ↔ *"이 문제의 이 지점이 아직 정해지지 않았습니다."* |
| **부연** | 모든 질문에 **권장안 + 근거**가 붙어, 사용자는 답을 새로 만들지 않고 **확인·교정**만 한다 |
| **전환 장치** | *"관점을 바꾸면 절차도 바뀝니다. 여섯 가지가 달라집니다."* |

---

#### S5 — 원리: 그립을 만드는 여섯 장치

| | |
|---|---|
| **독자 상태** | "말은 좋은데 구체적으로?" |
| **목적** | S1의 네 장면에 **일대일로 대응하는 처방**을 보여 논리를 닫는다 |
| **구성 원칙** | 기능 나열이 아니라 **"새는 지점 ↔ 장치"** 대응표 |

| 오너십이 새는 지점 | GRIP IT의 장치 |
|---|---|
| 근거가 부족해도 그럴듯한 항목을 지어낸다 | **재료 점검 게이트** — 기준선이 없으면 토픽을 뽑지 않습니다 |
| 전체 판을 모른 채 질문에 끌려간다 | **토픽 전체를 미리 보여주기** — 몇 번 문답할지 처음부터 압니다 |
| 뜻을 모르는 제안을 그대로 승인한다 | **용어 해설 + 설명적 대화체** — 이해한 것만 결정합니다 |
| AI가 제시한 보기 안에서만 고른다 | **기타(직접 입력) 상시 옵션** — 내 방식으로 답할 수 있습니다 |
| 정한 내용이 대화에 흩어진다 | **결정 기록부** — 무엇을 왜 정했는지 남습니다 |
| 다음 세션의 AI가 다시 제멋대로 정한다 | **규범 문서에 고정** — 한 번 정한 것은 다시 협상되지 않습니다 |

| | |
|---|---|
| **닫는 문장** | 에이전트는 재료를 점검하고, 선택지와 근거를 차려 놓고, 용어를 풀어 설명합니다. **결정은 사용자가 합니다.** |
| **전환 장치** | *"실제로는 이렇게 흘러갑니다."* |

> 각 장치는 **한 줄 요약 + 펼치면 근거**의 2단 구조를 권한다. 여섯 개를 모두 펼쳐 놓으면 S5에서 페이지가 무거워진다.

#### S6 — 증거: 한 세션을 처음부터 끝까지

| | |
|---|---|
| **독자 상태** | "정말 그렇게 동작하나?" |
| **목적** | **말하지 말고 보여주기.** 이 페이지에서 가장 공들일 섹션 |
| **소재** | 연구 도메인 시나리오 — 비개발 독자를 향한 포지셔닝을 동시에 증명한다 |

**보여줄 4컷**

```
1컷  재료 점검   R1 충족 / R2 없음 → 게이트 발동, A·B 두 갈래만 제시
2컷  토픽 원장   RESOLVED 0 / DROPPED 0 / TOTAL 4 — 앞으로 몇 번인지가 여기서 보인다
3컷  한 토픽     선택지 + 권장안·근거 + [용어] 해설 + 마지막에 "기타(직접 입력)"
4컷  반영 완료   근거 문서 / 규범 문서 / 기록부 세 줄
```

| | |
|---|---|
| **강조 포인트** | 2컷의 카운터와 3컷의 `기타` 옵션. 이 둘이 "가시성"과 "출구"를 눈으로 증명한다 |
| **전환 장치** | *"이 예시는 연구였습니다. 사업기획이라면, 서비스기획이라면요?"* |

**표현 방식 `[확정]` — 4컷을 세로로 나란히 둔다.** 스크롤하면 1컷부터 4컷까지 차례로 나오며, **이 데모 영역 안에서는** JS를 쓰지 않는다.

여기서 "JS를 쓰지 않는다"는 것은 사이트 전체가 아니라 **스킬 사용 예제의 시각적 제시에 국한된 규칙**이다. 히어로의 손 연출(§7-1)과 언어 전환은 JS를 쓴다. 데모만 정적으로 두는 이유는, 절차를 보여주는 자리에서 독자의 통제권을 빼앗지 않기 위해서다.

인터랙션을 포기한 대신 얻는 것이 있다. 네 컷이 한 흐름으로 이어져 **절차 전체가 한눈에 남고**, 2컷의 카운터와 3컷의 기타 옵션을 독자가 스크롤 중에 동시에 본다. 잃는 것은 "직접 넘겨보는" 체감이므로, 그 몫은 컷 사이 전환 문장으로 벌충한다.

- 각 컷은 실제 출력 형식 그대로 코드블록으로 싣는다. 재현이 아니라 인용이다
- 컷 사이에 한 줄 설명을 넣어 왜 그 화면이 나오는지 잇는다
- 4컷 전체를 하나의 영역으로 묶어, 스크롤 중에 "지금 데모를 보고 있다"가 유지되게 한다

## 6. 콘텐츠 원칙

1. **스킬의 언어 규칙을 페이지가 스스로 지킨다.** 완결 문장, 경어 기조, 감정 절제, 영문 용어는 `English Term(역어: 뜻풀이)`. 페이지가 규칙을 어기면 규칙의 설득력이 사라진다.
2. **숫자는 검증 가능한 것만 쓴다.** "몇 배 빨라진다" 같은 미측정 주장 금지. 쓸 수 있는 것은 구조적 사실뿐이다 — 도메인 5종, 재료 역할 5개, 장치 6개, 종료 사유 4종.
3. **한 섹션 한 메시지.** 두 개를 담고 싶으면 섹션을 쪼갠다.
4. **모든 주장 뒤에 근거 한 줄.** 스킬이 "권장안 + 근거"를 규칙으로 갖는 것과 같은 태도.

### 언어 범위 `[확정]`

**한·영 병행.** 저장소가 이미 README 한/영을 갖추고 있어 자산이 일관된다.

최소 투입 제약(§1-4)과 부딪히지 않도록 다음 방식으로 만든다.

- **한 장 안에 두 언어를 담고 JS로 전환한다**(→ §8-2 T4 확정). 페이지를 나누지 않으므로 링크·경로가 하나로 유지된다
- **시각 자산은 공유한다.** 표·코드블록·다이어그램·컬러·서체는 한 벌만 만든다
- **두 벌로 만드는 것은 카피뿐이다.** 영문 카피의 원천은 `README.en.md`이며, 새로 쓰지 않고 옮겨 다듬는다

이렇게 하면 늘어나는 작업은 카피 한 벌이고, 시각 작업량은 그대로다. 두 언어 카피가 한 파일에 함께 실리므로 초기 전송량이 늘고 검색엔진에는 기본 언어 한쪽만 잡힌다는 점은 감수한다.

## 7. 시각적 표현 기획 `[전 항목 확정]`

> 이 장은 전 항목이 확정되었다. 각 절의 표와 규칙이 제작의 기준이다.

### 7-1. 비주얼 컨셉 `[확정]`

**손과 쥠 — 스크롤에 반응하는 이미지 시퀀스로 구현한다.**

히어로에서 시작해 데모 영역까지 이어지는 하나의 연출이다.

```
1단계  양쪽에서 거대한 손이 들어와, 가운데 놓인 내용을 움켜쥐려 한다
2단계  스크롤을 내리면 양손이 가운데서 만나 움켜쥔다
3단계  쥐는 순간 밝은 빛 효과가 터진다
4단계  양손이 화면 하단으로 내려가, 위를 향해 펼쳐진 받침 형태가 된다
5단계  그 손 위에서 스킬 사용 단계 시연(S6 4컷)이 일어난다
```

| 항목 | 방식 |
|---|---|
| 이미지 | 손 시퀀스 **20장 내외**. 스크롤 위치에 예민하게 반응하도록 프레임을 촘촘히 둔다 |
| 모션 | **JS로 구현**한다. 스크롤 진행도에 프레임을 매핑한다 |
| 빛 효과 | 쥐는 순간의 빛 번짐과 잔상도 JS로 연출한다 |
| 반응형 | 화면 크기에 따라 프레임 수와 손 크기를 조정한다 |

이 연출이 페이지의 주된 시각 논거다. "실행은 놓고 결정은 쥔다"를 문장으로 설명하기 전에 화면이 먼저 보여주고, 마지막에 손이 받침이 되어 그 위에서 절차가 흐르는 구조가 스킬의 역할과 겹친다.

### 7-2. 컬러 시스템 `[확정]`

**밝은 테마 전용.** 다크 모드는 두지 않는다. 손 이미지 시퀀스가 밝은 바탕을 전제로 만들어지므로, 두 벌을 만들면 시퀀스를 다시 제작해야 한다.

| 역할 | 방향 |
|---|---|
| 바탕 | 햇볕처럼 따뜻하고 밝은 톤. 차가운 순백이 아니라 친숙하고 편안한 밝기 |
| 본문 텍스트 | **딥 네이비** — 검정 대신 써서 밝은 바탕과 부드럽게 붙되 신뢰감을 준다 |
| 구별 요소·강조 | **밝은 블루** — 링크, 섹션 구분선, 강조 텍스트, 설치 블록 테두리 |
| 손 연출의 빛 | 바탕보다 밝은 난색 계열. 쥐는 순간에만 등장한다 |
| 상태 3색 | RESOLVED / UNRESOLVED / DROPPED. **데모 블록 안에서만** 쓰고 본문에는 쓰지 않는다 |

두 계열의 역할이 다르다. **난색(햇볕)은 분위기를, 한색(네이비·블루)은 정보를** 맡는다. 정보를 전달하는 요소에는 난색을 쓰지 않는다.

상태 3색은 색만으로 구분되지 않게 한다. `RESOLVED` 같은 상태 문자열이 항상 함께 붙으므로, 색을 못 보아도 읽힌다.

### 7-3. 타이포그래피 `[확정]`

**무료 웹폰트 조합으로 간다.** 라이선스 확인 절차가 없고, 한글 고정폭까지 갖출 수 있다.

| 용도 | 서체 | 이유 |
|---|---|---|
| 헤드라인 | Pretendard 또는 Noto Sans KR의 굵은 굵기 | 한글 가독성이 확보되어 있고 굵기 단계가 넓다 |
| 본문 | 같은 계열의 보통 굵기 | 서체를 하나로 묶어 웹폰트 용량을 아낀다 |
| 코드·기록부 | D2Coding 또는 나눔고딕코딩 | **한글 고정폭이 맞는다.** 기록부 표의 세로 정렬이 여기 달려 있다 |

**용량 관리** — 본문 계열은 헤드라인과 같은 서체를 굵기만 달리해 쓴다. 서체 종류를 늘리지 않고 굵기로 위계를 만든다. 필요한 굵기만 골라 받는다.

**되돌아갈 자리** — 웹폰트가 늦게 뜨거나 실패해도 읽히도록 시스템 한글 서체를 대체 목록에 둔다. 특히 코드 블록은 대체 서체도 고정폭이어야 정렬이 무너지지 않는다.

### 7-4. 레이아웃 `[확정]`

**두 폭을 쓴다 — 본문은 좁게, 넓은 블록은 넓게.** 단일 컬럼 스크롤을 기본으로 하되, 요소에 따라 폭을 달리해 리듬을 만든다.

| 폭 | 쓰는 곳 |
|---|---|
| **좁은 폭** (읽기 편한 범위) | 모든 산문. 스토리 단계 S0~S9의 카피 |
| **넓은 폭** | S6 데모 4컷 · S7 도메인 표 · 오너십 대응표 · 다이어그램 |
| **전체 폭** | 히어로 손 연출. 화면을 가득 쓴다 |

섹션마다 여백으로 호흡을 끊는다. 스토리 단계가 아홉 개이므로 경계가 분명해야 독자가 지금 어느 단계인지 안다.

**폭이 바뀌는 것 자체가 신호다.** 좁은 폭에서 넓은 폭으로 넘어가면 "이제 보여주는 자리"라는 뜻이고, 다시 좁아지면 "설명으로 돌아왔다"는 뜻이다. 이 규칙을 지키면 소제목 없이도 구조가 읽힌다.

### 7-5. 핵심 다이어그램 `[확정]`

| **D1** | 그립 상태 | 실행(놓음) ↔ 이해·방향·결정(쥠)의 대비 | S2 |
| **D2** | 두 계층 | 기록계층 1파일 ↔ 확정계층(근거 문서/규범 문서) | S8 |
| **D3** | 세션 흐름 | 재료 점검 → 토픽 원장 → 한 토픽씩 → 반영 → 재개 | S6 도입 |

**히어로와 역할을 나눈다.** 손 연출이 감정과 은유를 맡으므로, 본문 다이어그램은 반대로 간다 — 장식을 덜어내고 구조만 보여준다. 화려한 히어로 뒤에 화려한 다이어그램이 이어지면 둘 다 흐려진다.

- 선 굵기와 색은 두 가지만 쓴다. 딥 네이비(구조)와 밝은 블루(강조)
- 글자는 SVG 안에 텍스트로 넣어 확대해도 깨지지 않게 한다
- D1은 히어로 손 연출과 주제가 겹치므로, 은유를 반복하지 말고 **놓음/쥠을 도식으로만** 표현한다

### 7-6. 인터랙션·모션 `[확정]`

**움직이는 곳은 두 군데뿐이다 — 히어로와 S1.** 나머지 본문은 움직이지 않는다.

| 위치 | 모션 | 이유 |
|---|---|---|
| **히어로** | 손 시퀀스 스크롤 연동 + 쥐는 순간의 빛(§7-1) | 페이지의 주된 시각 논거 |
| **S1 네 장면** | 스크롤에 따라 하나씩 순차 등장 | 네 장면이 차례로 쌓여야 "이게 다 내 얘기"라는 인식이 눌린다 |
| 그 밖의 본문 | 없음 | 요소마다 튀어나오면 "감정 절제" 톤과 어긋난다 |
| S6 데모 4컷 | 없음 | 데모 영역은 정적으로 둔다(§4-2 S6) |

S1에 모션을 두는 것은 장식이 아니라 **속도 조절**이다. 네 장면을 한 번에 보여주면 목록으로 읽히고, 하나씩 나오면 각 장면에서 잠깐 멈추게 된다. 이 섹션이 페이지 전체의 이탈률을 좌우하므로 그 멈춤이 필요하다.

히어로와 S1이 주의를 나눠 갖지 않도록, S1의 등장 효과는 **위치 이동 없이 나타나는 정도**로 절제한다.

### 7-7. 데모(S6) 표현 방식 `[확정]`

| 안 | 구현 부담 | 설득력 | 비고 |
|---|---|---|---|
| **A. 정적 코드블록 4개** | 낮음 | 중 | 가장 빠르게 낼 수 있음. 스크롤만으로 이해 가능 |
| **B. 단계 이동 인터랙션** | 중 | 높음 | 사용자가 직접 넘기며 "몇 번 문답하는지"를 체감 |
| **C. 자동 재생 애니메이션** | 높음 | 중 | 통제권을 뺏는 연출이라 **오너십 메시지와 상충**할 수 있음 |

**확정: A — 4컷 세로 나란히.** 최소 투입(§1-4)과 빌드 없는 한 장 구성(§8-1 T4) 안에서 고른 결과이며, 상세는 §4-2 S6에 적었다.

### 7-8. 반응형 `[확정]`

다크 모드는 두지 않는다(§7-2). 좁은 화면 처리는 블록마다 다르게 간다.

| 블록 | 좁은 화면에서 |
|---|---|
| **S7 도메인 표** | **도메인별 탭으로 접는다.** 한 번에 한 도메인만 보이고 탭으로 넘긴다 |
| S6 데모 4컷 · 기록부 블록 | 가로 스크롤 컨테이너로 감싼다. 원본 형태와 정렬을 유지한다 |
| 오너십 대응표 | 두 열이라 그대로 좁혀도 읽힌다 |
| 히어로 손 연출 | 프레임 수와 손 크기를 화면 크기에 맞춰 조정한다(§7-1) |

도메인 표만 탭으로 접는 이유는, 이 표가 **"개발자용이 아니다"를 증명하는 자리**여서 좁은 화면에서 뭉개지면 안 되기 때문이다. 독자가 자기 도메인 열을 온전히 읽을 수 있어야 한다.

기록부 블록에 가로 스크롤을 쓰는 것은 반대 이유다. 이 블록은 **형태 자체가 메시지**라서, 접거나 줄이면 "한 파일에 이렇게 남는다"가 전달되지 않는다.

탭 전환은 언어 전환 JS와 같은 자리에서 처리한다. 데모 영역의 "JS를 쓰지 않는다" 규칙(§4-2 S6)은 데모 4컷 자체에만 적용되므로 충돌하지 않는다.

### 7-9. 접근성 `[확정]`

**별도 목표를 두지 않고 기본값에 맡긴다.** 접근성 점검을 작업 항목으로 세우지 않는다.

다만 다른 결정 덕분에 자연히 확보되는 부분은 그대로 유지한다.

- 상태는 색만이 아니라 `RESOLVED` 같은 문자열이 함께 붙는다(§7-2) — 색을 못 보아도 읽힌다
- 본문은 딥 네이비, 바탕은 밝은 톤이라 대비가 확보된다(§7-2)
- 데모 4컷은 정적 블록이라 키보드 조작이 필요 없다(§4-2 S6)

**감수하는 것** — 히어로의 스크롤 연동 손 연출은 20장 시퀀스를 빠르게 넘기므로, 움직임에 민감한 이용자에게 부담이 될 수 있다. 이 부분은 별도 대응 없이 둔다.

## 8. 배포·기술

### 8-1. 확정 — 기준 버전 고정

이 페이지가 인용하는 모든 규칙·어휘·예시는 아래 버전에 **고정**한다.

```
기준 스킬 버전   grip-it @ b1df6e1
기준 문서        .claude/skills/grip-it/SKILL.md · README.md · README.en.md
고정 어휘        기록계층 / 확정계층 · 근거 문서 / 규범 문서 ·
                 결정 기록부(Grip Register) · docs/grip/GRIP_REGISTER.md ·
                 재료 역할 R1 목적 / R2 범위 / R3 대상 / R4 제약 / R5 진척 ·
                 3대 핵심 요건 = 범위 한정 / 전체 가시화 / 즉시 반영 ·
                 종료 사유 ALL_RESOLVED · USER_PAUSED · MATERIAL_PENDING · BUDGET_REACHED
```

카피·데모·표는 위 어휘만 쓴다.

**제작 제약 (T1 확정 → T6에서 상향)** — 중간 투입. 페이지 한 장 · 손 이미지 시퀀스 20장 내외 · 스크롤 모션 구현 · 1~2주 규모. 투입은 히어로 손 연출에 집중하고 본문 섹션은 기존 자산을 인용한다.

**표기 규칙 (T2 확정)** — 브랜드는 `GRIP IT`, 스킬·명령·경로는 `grip-it`. 카피 전반에 이 구분을 적용한다.

**언어 범위 (T3 확정)** — 한·영 병행. 시각 자산 공유, 카피만 두 벌. 영문 원천은 `README.en.md`.

**구현 방식 (T4 확정)** — HTML 한 장에 JS 스크립트로 한·영 전환하고 CSS는 공유 한 벌. 빌드 단계 없음.

**데모 표현 (T5 확정)** — S6 4컷을 세로로 나란히. 컷 사이 전환 문장으로 흐름을 잇는다. **"JS를 쓰지 않는다"는 규칙은 이 데모 영역에만 적용**되며, 히어로 손 연출과 언어 전환에는 JS를 쓴다.

**마무리 문장 (T18 확정)** — 수미상관. 히어로의 "실행은 맡기고, 결정은 쥔다"를 권유형으로 바꿔 설치 블록 아래에 놓는다.

**소스 위치 (T17 확정)** — `grip-it-skill` 저장소 안 `web/` 폴더. 스킬이 바뀔 때 페이지를 같은 커밋에서 함께 고칠 수 있어, 인용한 규칙과 페이지가 어긋나지 않는다.

**모션 범위 (T16 확정)** — 히어로 손 연출과 S1 네 장면 순차 등장, 두 군데만 움직인다. S1의 등장 효과는 위치 이동 없이 절제하고, 그 밖의 본문과 데모 4컷은 정적으로 둔다.

**반응형 (T15 확정)** — 좁은 화면에서 도메인 표는 도메인별 탭으로 접고, 데모 4컷과 기록부 블록은 가로 스크롤로 감싸 형태를 유지한다. 탭 전환은 언어 전환 JS와 같은 자리에서 처리한다.

**레이아웃 (T14 확정)** — 세 가지 폭을 쓴다. 산문은 좁은 폭, 데모·표·다이어그램은 넓은 폭, 히어로는 전체 폭. 폭이 바뀌는 것 자체가 "설명 / 보여주기"의 신호가 된다.

**계측 (T13 확정)** — 계측하지 않는다. 분석 도구를 붙이지 않으며, §1-2의 지표 표는 설계 지향점으로만 유지한다.

**도메인 (T12 확정)** — `grip-it.work`. 이미 구입해 두었으며, 정적 호스팅에 연결해 이 주소를 정식 주소로 쓴다. 호스팅 기본 주소는 여기로 넘긴다.

**호스팅 (T11 확정)** — Vercel 등 정적 호스팅. 저장소를 연결해 푸시하면 배포되는 방식으로 둔다. 빌드 단계가 없으므로 출력 디렉터리만 지정하면 된다.

**접근성 (T10 확정)** — 별도 목표를 두지 않는다. 다른 결정으로 확보되는 부분(상태 문자열 병기, 본문 대비, 정적 데모)만 유지하고, 히어로 모션에 대한 대응은 하지 않는다.

**다이어그램 (T9 확정)** — 선도형 SVG 3종(D1 그립 상태 · D2 두 계층 · D3 세션 흐름). 딥 네이비 선과 밝은 블루 면만 쓰고, 히어로가 은유를 맡으므로 본문 다이어그램은 구조만 보여준다.

**타이포그래피 (T8 확정)** — 무료 웹폰트 조합. 헤드라인·본문은 한 계열을 굵기만 달리해 쓰고, 코드·기록부는 한글 고정폭 서체를 쓴다. 대체 서체도 고정폭으로 둔다.

**컬러 시스템 (T7 확정)** — 밝은 테마 전용, 다크 모드 없음. 바탕은 햇볕 톤, 본문은 딥 네이비, 구별 요소는 밝은 블루. 난색은 분위기, 한색은 정보를 맡는다.

**비주얼 컨셉 (T6 확정)** — 손과 쥠. 히어로에서 양손이 모여 쥐고, 빛이 터지고, 하단으로 내려가 받침이 되어 그 위에서 시연이 흐른다. 손 이미지 20장 내외 시퀀스를 JS로 스크롤에 연동한다. 전체 테마는 밝게 가되 텍스트·레이아웃 구별 요소에 딥 네이비와 밝은 블루를 쓴다(상세는 T7).
